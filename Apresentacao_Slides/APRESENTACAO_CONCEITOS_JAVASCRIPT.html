Conceitos ligados ao código real do projeto

O projeto

Uma aplicação.
Dois lados.

O UniDuniTê cadastra participantes e os divide aleatoriamente em grupos equilibrados.

interface React→API Express→serviço→SQLite

O frontend também transforma e valida listas antes de mostrar resultados e prévias de importação.

IDEIA-CHAVE

Conceito não é enfeite

Cada recurso da linguagem ajuda a resolver uma necessidade concreta — com validação no navegador e no servidor.

01 · Tipos, conversão e validação

Formulário entrega texto.
O sorteio precisa de números.

// App.js — os campos chegam como strings const min = Number(minInput); const max = Number(maxInput); if (!Number.isInteger(min) || !Number.isInteger(max)) { // interrompe e informa a pessoa }

Também na importação

Nomes são normalizados, comparados sem diferenciar maiúsculas/minúsculas e rejeitados se vazios, duplicados ou longos demais.

Comparações estritas (`===`, `!==`) evitam surpresas de conversões implícitas.

O backend valida novamente: as regras não dependem só do navegador.

02 · Truthy, falsy e valores opcionais

Ausência também
é um estado.

ESTADO VAZIO

Sem participantes

O sorteio é interrompido com uma mensagem clara, em vez de tentar produzir grupos sem dados.

VALOR PADRÃO

?? e ||

Configurações opcionais recebem um padrão quando necessário; cada operador tem uma regra diferente para valores falsy.

ACESSO SEGURO

?.

Detalhes de erro que talvez não existam podem ser consultados sem disparar uma segunda exceção.

A área de resultados também tem um estado inicial antes do primeiro sorteio.

03 · const, let e escopo de bloco

Estável por padrão.
Mutável quando precisa.

NO PROJETO

const para referências estáveis

let aparece em mudanças controladas, como o índice do embaralhamento ou um motivo de rejeição calculado durante a operação.

O projeto não usa var.

// Fisher–Yates simplificado const shuffled = [...values]; for (let i = shuffled.length - 1; i > 0; i--) { // troca posições na cópia }

A lista original continua na ordem do painel; o resultado sorteado aparece nos grupos.

04 · Funções, callbacks e closures

Ações da interface
viram funções.

CALLBACKS

Responder a eventos

onClick, onChange e onSubmit conectam botões e formulários às operações de adicionar, sortear e editar.

FUNÇÕES DE ORDEM SUPERIOR

Transformar coleções

map, filter, forEach e some recebem callbacks para percorrer e verificar listas.

Uma closure permite ao callback acessar o estado e os índices da renderização em que foi criado.

Na edição de grupos, a ação de mover alguém conhece o grupo de origem e o destino sem depender de variáveis globais.

05 · Objetos, arrays e coleções

Dados organizados
para cada tarefa.

Participante é objeto. Grupo é array.

Métodos de coleção deixam a intenção visível:

map → construir filter → selecionar some → verificar forEach → processar Set → detectar duplicatas

A mesma estrutura de dados alimenta a lista numerada, a prévia de importação e os cartões de grupo.

A distribuição garante que cada participante entre uma vez; limites ajudam a manter os grupos equilibrados.

06 · Cópia, referência e spread

Editar sem estragar
o original.

// uma nova lista para embaralhar const copy = [...participants]; // um novo objeto de estado return { ...state, revealed: next }; // uma nova lista de grupos para editar const draft = teams.map(team => [...team]);

O fluxo de edição deixa isso visível

Editar→rascunho→Salvar

Mover participantes altera a cópia. Salvar aplica; Cancelar descarta. Novas referências também permitem ao React detectar atualizações.

07 · Assincronismo, Promises e async/await

Esperar sem
congelar a interface.

async function loadParticipants() { setBusy(true); try { const data = await participantsApi.list(); setParticipants(data); } finally { setBusy(false); } }

O exemplo resume o padrão: aguardar a API e sempre liberar o estado de carregamento.

ONDE ACONTECE

API, arquivo e controlador

  • fetch busca e interpreta respostas HTTP.
  • file.text() lê o arquivo antes da prévia.
  • Controladores aguardam serviços antes da resposta.

Na interface, carregamento e controles desabilitados tornam a espera explícita.

08 · Tratamento de erros

Falha não é
sucesso disfarçado.

FRONTEND

Informar e recuperar

A interface mostra o problema e libera o estado de atividade, inclusive quando a chamada falha.

SERVIÇO

Regras explícitas

Dados inválidos e nomes duplicados viram erros conhecidos, não atualizações silenciosas.

API

Resposta estruturada

O middleware converte erros conhecidos em respostas adequadas e registra falhas inesperadas.

Exemplo: nome duplicado aparece como duplicidade — o campo não é tratado como se a inclusão tivesse dado certo.

09 · Módulos: ESM e CommonJS

Responsabilidades separadas.
Formatos diferentes.

FRONTEND · ESM

import / export

O componente principal reúne painéis, seletor de tema e utilitários importados de arquivos próprios.

BACKEND · COMMONJS

require / module.exports

O pacote configura CommonJS; rotas, serviços e repositórios separam a API da persistência e das regras.

rota→controlador→serviço→repositório

Uma distinção importante

Nem todo conceito
virou uma feature.

Os fundamentos continuam relevantes, mas a apresentação não deve atribuir ao projeto uma técnica que ele não usa diretamente.

Sem uso direto equivalente

varhoisting como estratégia call / apply / bindreduce

Uma ressalva: Promise.all

Não faz parte do fluxo normal do produto. Aparece nos testes da API para verificar criações concorrentes de nomes.

No backend, this.repository é usado pela instância do serviço; isso não torna call, apply ou bind uma técnica central.

Evidências e fechamento

Conceitos em uso.
Comportamentos testados.

FRONTEND

Importação

Testes verificam normalização e separação entre nomes válidos e rejeitados.

FRONTEND

Sorteio

Testes verificam revelação progressiva dos grupos e formatação do resultado.

BACKEND

API

JavaScript transforma regras em uma experiência previsível — quando os dados, estados e falhas são tratados com clareza.
